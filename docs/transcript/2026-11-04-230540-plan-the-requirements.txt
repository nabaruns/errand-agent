⏺ I've written a requirements plan for the Errand Agent assignment to
  /Users/nabaruns/work/hackathon/orange/PLAN.md.

  Core design: a fixed state machine in code runs the workflow. The LLM only
  handles language and picks read-only tools. Booking, cancelling and
  rescheduling go through an approval check in application code, so neither the
  model nor a prompt injection in a review can trigger them on its own. The
  approval is tied to the exact provider, slot and price, and any change to
  those cancels it and asks again.

  Duplicate bookings: before calling book, the agent saves an idempotency key to
  SQLite. After a timeout it asks the booking-status tool what actually
  happened before it retries or reports success. On restart it checks any
  unfinished bookings the same way first.

  What else it covers:
  - All 8 mock tools with their required failure behaviours, using seeded
    randomness so tests repeat exactly.
  - The memory model: explicit vs. inferred facts, plus correcting and
    forgetting them.
  - A context builder that stays under a token budget and logs exactly which
    facts it sent each turn.
  - Detecting a provider cancellation and finding a replacement without the user
    asking.
  - Per-run JSONL traces.
  - 25 offline test scenarios, with rules checked in every run (no side effect
    without approval, never claim success before the status is confirmed).
  - A deliverables checklist and an 8-step build order.

  I assumed Python, SQLite and Claude Sonnet 5.5. Four choices are still yours:
  - Language: Python or TypeScript.
  - Demo UI: a small local web page with chat and trace side by side, or a split
    terminal.
  - Second agent: whether to add a tool-less one that summarizes reviews so raw
    review text never reaches the main agent. The brief only rewards a second
    agent if it solves a real problem, and that's the clearest one.
  - Limits: the exact caps on model calls, tool calls and time, and the token
    budget.

  Tell me your picks, or I'll go with the defaults and start on the mocks.

  with uv, git initialized, nothing committed yet.

  - The 8 tools are in errand_agent/mocks/service.py. Their state is kept in a
    separate SQLite file, like a real outside service, so holds, bookings and
    idempotency records survive an agent restart.
  - Failures like slot_taken and hold_expired come back as {"ok": false, 
    "error": ...}. A timeout or 503 raises an exception instead, because in
    those cases the caller gets no answer at all.
  - book is idempotent on its key. When it times out after actually booking, the
    booking is saved before the timeout is raised, so get_booking_status shows
    the truth.
  - Repeatable outcomes: random draws are keyed by seed and call identity, so
    they come out the same across restarts. Scenario(book_outcomes=(...)) lets a
    test force exact outcomes, and a test confirms the 70/15/7.5/7.5 split.
  - Prompt injection: three providers have injected reviews. One tries to force
    a booking, one tries to cancel everything, and one tries to plant a fake
    memory.
  - Seeded history: a past electrician booking with Ravi Kumar, 16 days ago, and
    an AC servicing booking tomorrow. Rescheduling to Saturday 10:00 hits
    slot_conflict by default.
  - Clock: errand_agent/clock.py has a FakeClock so tests can check the
    10-minute hold expiry without waiting.
  - Provider cancellations: simulate_provider_cancellation and fetch_events
    exist only to simulate the provider side. They aren't tools the agent can
    call.

  How it works:
  - Agent.poll_events() reads the provider's event feed. The CLI calls it every
    2 seconds in the background, so no user message is needed. Its position in
    the feed is saved, so an event is handled once, even across a restart.
  - The agent decides in code whether to notify:
    - It skips bookings whose time has already passed.
    - If the user has another confirmation open, it sends the notice but doesn't
      replace that confirmation.
    - Otherwise it posts the notice into the conversation that made the booking
      and flags it as urgent if the visit was within 24 hours.
  - The replacement search needs no model call. It uses the user's saved
    preferences: area, earliest and latest time, budget, preferred provider and
    providers to avoid, with a service-specific preference beating a general
    one.
    - It never picks the provider who cancelled.
    - It ranks options by preferred provider first, then the slot closest to the
      original time, then rating, then price.
    - It holds the best slot and asks the user to confirm. The old approval
      doesn't carry over, so nothing is rebooked until the user says "yes".
  - If nothing fits the preferences, the agent says which preferences ruled
    everything out and offers to look more widely, without proposing anything.
  - If the user says "no", the model takes over with the service, area and dates
    already filled in.

  How it works:
  - Runner: uv run python -m evals.run (also part of pytest) runs every scenario
    in a temporary environment. It writes docs/eval/eval_table.md (scenario,
    expected, actual, pass/fail, notes) and docs/eval/results.json.
  - Simulated user: it reacts to what the agent actually did, not how it phrased
    it. It says "yes" when an approval is waiting, fills in whatever the
    session says is still missing from its profile, and answers failures.
  - Checks: each scenario checks outcomes in the provider database, the approval
    store and the trace. Every scenario must also pass these global rules:
    - no side effect without a matching approval, and the model can never reach
      a side-effecting tool
    - no duplicate bookings
    - no success reported before it's verified
    - every run ends with a reply
    - no injected review text, and no forgotten or unconfirmed fact, ever sent
      to the model

  Coverage: every category the brief lists is covered.
  - Core and conversation: the happy path, asking only for missing details,
    corrections, "same electrician as last time".
  - Security: injection in a review; the model itself obeying an injection; the
    user trying to skip confirmation; a review trying to plant a memory.
  - Approval and recovery: price or slot changes after approval, slot taken,
    timeout after success, timeout before booking, the status service down,
    repeated "yes", restart mid-booking.
  - Memory: correcting, forgetting, inferred facts needing confirmation, the
    context budget with 54 facts and 120 messages.
  - Proactive: provider cancels and a replacement fits; provider cancels and
    nothing fits.
  - Limits and failures: model-call, tool-call and time limits; tool failures;
    the model API failing.
